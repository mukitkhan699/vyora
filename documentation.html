Project Documentation · Static Code Audit

VYORA
Global Real-Time Network

A decoupled social platform built with React 19, Vite, Tailwind CSS v4 and an Express API. The frontend is configuration-free; the backend owns branding, feature gates, CDN routing, file storage and PostgreSQL access. This document describes the system and records the results of a static code audit performed on the repository.

Static audit complete Runtime not executed No dependencies installed Audit date: 2026-11-03 Node detected: v24.21.0

01Overview

VYORA is a full-stack social-network demo with a Twitter/X-style interface. Users can publish posts (with text, media, polls, replies and quotes), like, repost, bookmark, follow other users, vote in polls, browse trends, edit profiles, exchange direct messages and authenticate against the backend.

The project is split into two logical halves:

Frontend

A React single-page application mounted at #root. All configuration is fetched from /api/config; no API keys or limits are hardcoded in the client. The UI is responsive with a desktop three-column layout and a mobile bottom navigation bar.

Backend

An Express 4 API with an in-memory data engine and an optional PostgreSQL adapter. The server also handles file uploads, serves uploaded media, exposes CDN health checks, and can return its own source code for inspection through /api/backend-code.

Design intent

The frontend is intentionally dumb. Branding, maximum post length, feature flags, media presets, CDN URLs and database details are all delivered by the server. This is stated repeatedly in the UI copy and reflected in the code structure.

02Audit Verdict

Can it run fully without errors? — Not confirmed.

The source is coherent, the TypeScript server files pass a syntax check, and the committed frontend/backend build artifacts parse successfully. However, the app was not executed end-to-end because this environment has no node_modules, no npm, no tsx and no TypeScript compiler. Per the instruction not to install packages or tools, no dependencies were installed. A full npm install + npm run lint + npm run build verification is therefore still required.

PASS · Syntax

All 9 inspected server/type TypeScript files pass node --experimental-strip-types --check. Both committed bundles parse.

PARTIAL · Build

Existing dist/ and server-dist/ artifacts are valid, but a fresh build was not attempted.

FAIL · Runtime

No live server, API request or browser test was possible without dependencies. Behaviour is assessed from source only.

Summary

The application is structurally complete and likely to build, but it is not production-correct as-is. The most significant issues are a partially implemented PostgreSQL layer, globally shared notifications, globally shared poll-vote state, a media-only post rejection, and an authentication fallback that weakens password checks. These are described in detail in Bugs & Risks.

Request flow

  1. The browser loads index.html, which mounts src/main.tsx into #root.
  2. App.tsx wraps the UI in ThemeProvider and AuthProvider.
  3. AuthProvider fetches /api/config, /api/users, demo accounts and session state.
  4. Client calls go through src/services/api.ts, which prefixes /api and attaches the session token.
  5. Express routes call dbAdapter, which primarily reads and writes the in-memory store.
  6. If a PostgreSQL pool connects, new posts are also written to Postgres (fire-and-forget).

Production

# Build the frontend into dist/
npm run build

# Run the TypeScript server directly (requires dev dependency tsx)
NODE_ENV=production npm start

# Alternative: run the pre-bundled backend
node server-dist/server.cjs
Production notes

npm run build only builds the frontend. There is no script that compiles server.ts into server-dist/server.cjs; that bundle was produced separately with esbuild. Also, npm start invokes tsx, which is a dev dependency, so a production install using --omit=dev will fail to start.

npm run build    # vite build

Important database caveat

DATABASE_TYPE=memory is not fully honoured. PostgresService creates a pool whenever a host or URL is configured, and SQL_HOST defaults to localhost. A connection attempt therefore occurs even in memory mode; it fails gracefully after the timeout.

14Bugs & Risks

Findings are ordered by practical impact. None of these are syntax errors; they are behavioural or security defects found by reading the code.

#SeverityFindingLocation
1HIGH PostgreSQL persistence is effectively non-functional. Only new posts are written to Postgres; users are never inserted, so the author_id foreign key fails and the insert is swallowed by a catch. No reads come from Postgres. server/db/adapter.ts:156-169
2HIGH Notifications are global. getNotifications(userId) ignores the user and returns the shared array; read-all mutates every user's notifications. server/db/adapter.ts:485-492
3HIGH Authentication bypass. A supplied password is accepted if it matches the stored password or the literal vyora123, so demo credentials unlock accounts that have custom passwords. server/db/adapter.ts:293
4HIGH Unauthenticated requests impersonate a user. When no token is supplied, getUserId returns user_mukit, so protected actions can be performed without signing in. server/routes/api.ts:10-21
5MED Poll vote state is shared. userVotedIndex is stored on the single shared poll object, so once one user votes every user sees the voted state and cannot vote. server/db/adapter.ts:253-262
6MED Media-only posts fail. The composer allows submission with media and no text, but the server rejects any post whose trimmed content is empty. server/routes/api.ts:371-374
7MED Upload MIME types are not validated. allowedMimeTypes is declared but never enforced; any base64 payload is accepted and served back. server/routes/api.ts upload handler; server/config.ts:83
8MED CORS is fully open. Access-Control-Allow-Origin: * is combined with token auth, which is acceptable for a demo but unsuitable for production. server/index.ts:14
9MED Demo credentials are publicly enumerable. /api/auth/demo-accounts returns every account's default password. server/routes/api.ts auth demo route
10MED Profile updates are unrestricted. PUT /api/users/profile passes the request body straight into the user object, allowing fields such as verified or counts to be changed. server/db/adapter.ts updateProfile; server/routes/api.ts
11LOW Bookmarks header reads the wrong key. It looks for x_active_user_handle, while the app stores x_active_user_id, so it always displays @mukitk. src/components/bookmarks/BookmarksView.tsx:48
12LOW Messages pane starts empty. selectedUser is initialised from an empty allUsers array and never updates when users finish loading. src/components/messages/MessagesView.tsx:15
13LOW CDN card can render empty. The sidebar snapshots CDN health on mount, before AuthProvider finishes fetching config, and never refreshes automatically. src/components/layout/RightSidebar.tsx:30-33
14LOW Database mode is not honoured. A pool is created whenever a host/URL exists; SQL_HOST defaults to localhost, so memory mode still attempts a connection. server/db/postgres.ts:17-35
15LOW Light theme is incomplete. Many components hard-code dark backgrounds and white text, so switching to light leaves parts of the UI dark or low-contrast. Various components
16LOW “Copy link” deep links do not work. The copied ?post=… URL is never parsed on load to open the thread. src/components/feed/PostCard.tsx:120-126
17NOTE Dead code and stale metadata. Unused components, unused dependencies, old README/Gemini instructions, Firebase files, and X-vs-VYORA branding inconsistencies remain in the repo. Multiple files

Additional observations

  • Files are stored in memory. Uploaded media disappears on server restart; no disk or object storage is used.
  • Post deletion leaves orphaned state. Related likes, bookmarks and notifications are not cleaned up.
  • Quote-post counts are one-way. Creating a quote increments the quoted post's repost count but removing it does not decrement.
  • Registration auto-follow is asymmetric. The new user follows user_mukit, but Mukit's follower count is not incremented.
  • Seed notification text still references “X” rather than VYORA.
  • Upload limit mismatch. The server advertises 10 MB, but base64 inflation inside a 10 MB JSON body means files near that size will be rejected by Express first.
  • No rate limiting, input sanitisation, CSRF protection, or password hashing. Passwords are stored in plain text in memory.
  • Committed Firebase API key. Client-side Firebase keys are normally public, but the unused config should be removed or restricted to avoid confusion.
  • Production server bundle is not reproducible from package scripts. server-dist/server.cjs must currently be generated manually with esbuild.

15Fix Checklist

Suggested order for turning this demo into a reliable application:

  1. Install dependencies and run npm run lint, npm run build, then start the server.
  2. Seed or upsert users into PostgreSQL before writing posts; wrap writes in transactions; read from Postgres when connected.
  3. Scope notifications by recipient and add a recipient field to every generated notification.
  4. Store poll votes per user (for example, Map<userId:postId, optionIndex>).
  5. Allow media-only posts by skipping the content check when media is present.
  6. Remove the || password === 'vyora123' bypass; hash passwords; return 401 when no token is supplied.
  7. Whitelist fields accepted by the profile update endpoint.
  8. Enforce allowedMimeTypes and the advertised upload size.
  9. Add tests for auth, posts, poll voting, bookmarks and notifications.
  10. Fix the bookmark key, message selection, CDN refresh and light-theme styling.
  11. Remove unused components/dependencies and update README, metadata and .env.example branding.
  12. Add a build script for the server bundle and a production-safe start path.
Bottom line

VYORA is a well-structured prototype with a clean API boundary and a polished UI. It is not yet a fully correct or production-ready system: the data layer is only half integrated with PostgreSQL, several features are global instead of per-user, and authentication needs hardening. The code does not show syntax errors, but full “works without errors” status requires the dependency-backed test run described above.
